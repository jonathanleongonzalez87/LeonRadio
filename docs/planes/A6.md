Decisiones:
- **Patrocinio es un tipo de Contrato** (`tipo = pauta | patrocinio`), no una entidad aparte: tiene los mismos datos (cliente, vigencia, valor, descripción) y lo que entrega al aire se mide igual (cuñas o presentaciones grabadas = compromisos). Lo que lo distingue —el programa patrocinado— no puede referenciarse todavía (ver abajo). Las menciones en vivo sin archivo no pasan por el historial y quedan fuera (deuda).
- **Compromiso = la tabla `commitments` existente, convertida en entidad gestionada** por migración aditiva. Es la única forma de que `playlog.commitment_id` (ya creada en v1, con `REFERENCES commitments(id)`) siga sirviendo a A7 sin reconstruir `playlog` (tabla de Al Aire, historial inmutable). Reconstruir `commitments` para quitar el `NOT NULL` de `client` se descarta: con `foreign_keys=ON` (que `migrate` no puede apagar dentro de su transacción) `DROP TABLE` dispara `ON DELETE SET NULL` y borraría los `commitment_id` del historial, y `RENAME` reapuntaría `playlog` a la tabla vieja.
- **Columnas de v1**: `client` es `NOT NULL` y no se puede cambiar sin reconstruir. Para filas nuevas Producción guarda el marcador fijo `CLIENTE_HEREDADO = "(ver contrato)"`; el cliente real sale siempre de `contrato_id → contrato.cliente_id → cliente`. Nunca se copia el nombre del cliente. `client` y `contract_ref` solo se muestran en filas antiguas sin contrato («(sin contrato) · <client>»). Alternativa que se descartó para no tocar el núcleo: un `Field(default=...)` en `entities.py` (ver Riesgos).
- **Programa (S10 pendiente)**: hoy **no** se crea ninguna columna `programa_id`. SQLite no permite añadir `REFERENCES` a una columna existente, y declarar `ref="programa"` sin la entidad hace fallar `validate()`. Cuando S10 mergee, una migración nueva de Producción (`ALTER TABLE contrato ADD COLUMN programa_id INTEGER REFERENCES programa(id)` + `Field("programa_id", "int", ref="programa")` + un select en el formulario) cierra el vínculo sin tocar nada de lo existente; mientras tanto, el programa patrocinado se escribe en `descripcion` (el formulario lo sugiere en el `placeholder`). Queda en la deuda con su SQL exacto.
- **Datos personales mínimos**: Cliente solo guarda `nombre` y `notas`; sin NIT, documento, teléfono, correo ni dirección (la facturación, B1, decide qué necesita y con qué cuidado). El `placeholder` de Notas dice «Sin teléfonos, correos ni documentos». Pruebas y docs con nombres inventados.
- **Dinero**: `contrato.valor_cop` entero en pesos colombianos (el COP no usa centavos en la práctica), opcional y ≥ 0. Sin moneda configurable, impuestos ni saldos (B1).

### Migración (`estaciones/produccion/migraciones.py::m4_comercial`)
Solo `sqlite3` y `datetime`, SQL literal, idempotente:
```python
STD = """archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1)),
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL, created_by TEXT NOT NULL, updated_by TEXT NOT NULL"""

def m4_comercial(conn):
    conn.execute(f"""CREATE TABLE IF NOT EXISTS cliente (id INTEGER PRIMARY KEY,
        nombre TEXT NOT NULL, nombre_norm TEXT NOT NULL UNIQUE, notas TEXT, {STD})""")
    conn.execute(f"""CREATE TABLE IF NOT EXISTS contrato (id INTEGER PRIMARY KEY,
        codigo TEXT NOT NULL UNIQUE, cliente_id INTEGER NOT NULL REFERENCES cliente(id),
        tipo TEXT NOT NULL CHECK (tipo IN ('pauta','patrocinio')), desde TEXT NOT NULL, hasta TEXT NOT NULL,
        valor_cop INTEGER CHECK (valor_cop IS NULL OR valor_cop >= 0), descripcion TEXT, {STD})""")
    cols = {r["name"] for r in conn.execute("PRAGMA table_info(commitments)")}
    for name, ddl in (("contrato_id", "INTEGER REFERENCES contrato(id)"),
                      ("archived", "INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1))"),
                      ("created_at", "TEXT NOT NULL DEFAULT ''"), ("updated_at", "TEXT NOT NULL DEFAULT ''"),
                      ("created_by", "TEXT NOT NULL DEFAULT ''"), ("updated_by", "TEXT NOT NULL DEFAULT ''")):
        if name not in cols:
            conn.execute(f"ALTER TABLE commitments ADD COLUMN {name} {ddl}")
    now = datetime.now(timezone.utc).isoformat(timespec="milliseconds")
    conn.execute("UPDATE commitments SET created_at = ?, updated_at = ?, created_by = 'sistema', updated_by = 'sistema' "
                 "WHERE created_at = ''", (now, now))
    # índices: cliente(nombre, id), contrato(cliente_id), contrato(desde), commitments(contrato_id), commitments(window_start, id)
```
(Comprobado en el equipo con SQLite 3.53.4: `ADD COLUMN … REFERENCES` con default NULL y `ADD COLUMN … NOT NULL DEFAULT … CHECK` funcionan con `foreign_keys=ON`.) Las filas antiguas quedan con `contrato_id NULL`: aparecen en «Pauta» como «(sin contrato)» y se les asigna uno desde el formulario. Sin relleno automático de clientes a partir de `client` (hoy ningún código escribe `commitments`; la base real casi seguro tiene 0 filas: se confirma en la verificación). La copia previa a migrar ya la hace S5.

Regla anti-choque (de S8): si S10 mergea antes y toma `m4`, esta función se renumera a `m<N>_comercial` al rebasar; quien ya migró su base local con la numeración vieja la restaura de `copias\` o usa otra base.

def preparar(reg: entities.Registry, tz, entidad: str, actual: dict | None, valores: dict) -> dict:

- **Cliente**: claves `nombre`, `notas`; pasa tal cual (el `Writer` valida y normaliza).
- **Contrato**: `codigo` (strip + mayúsculas), `cliente_id`, `tipo`, `desde`, `hasta` (AAAA-MM-DD; `hasta >= desde` combinando con `actual`), `valor_cop` (int o texto: se quitan «$», espacios y puntos de miles; debe quedar solo dígitos; «,» → `ValueError("el valor va en pesos, sin centavos")`), `descripcion`.
- **Compromiso**: claves `contrato_id`, `asset_id`, `campana` → `campaign`, `cantidad` → `plays_required` (entero ≥ 1), `desde`/`hasta` (fechas locales, `hasta` incluido) → `window_start = medianoche local de desde` y `window_end = medianoche local del día siguiente a hasta`, ambos en UTC con `datetime.isoformat()`; deben caer dentro de `contrato.desde..hasta`; `franja_desde`/`franja_hasta` → `daypart_*` (ambos o ninguno, `^([01]\d|2[0-3]):[0-5]\d$`, distintos; si inicio > fin cruza la medianoche); `notas` → `notes`. La pieza debe existir, estar activa (`ctx.entities.get("pieza", id)`) y tener `kind == "spot"`. En `crear` se agrega `client = CLIENTE_HEREDADO`. Cualquier otra clave → `ValueError("«Compromiso» no tiene el campo «…»")`.
- **Archivar/restaurar** con las reglas del criterio 10 (consultas `reg.list(..., where={"cliente_id": id})`, `limit=1`).
- Zona horaria: `ZoneInfo(host.config["timezone"])` (America/Bogota en `station.json`); si falla, la del equipo, igual que `builtin._station_tz` (se repiten las 4 líneas; no se importa nada de `builtin`, que es de Al Aire).

### Panel «Comercial» (`estaciones/produccion/paneles.py`)
`ComercialPanel(sdk.Editor)`: `id="produccion.comercial"`, `label="Comercial"`, `icon="▦"`, `station="produccion"`. Solo elementos existentes de `uischema`: `label`, `kv`, `button`, `table` con `UI.actions`, `form`, `tabs`.

Limitación que manda el diseño: `ui.form` envía **un solo campo por cambio** y **sin argumentos** (`runCommand(n.command, {[f.key]: v})` en `renderer.js`). Por eso la edición usa una **selección en el estado** (mismo patrón que `explorer.*` en `builtin`):
- `host.state["produccion.sel"] = {"entidad": "contrato", "id": 7}` (editar) o `{"entidad": "contrato", "id": None, "borrador": {...}}` (nuevo). Lo fijan `produccion.ver {entidad, id?}` (botón «Nuevo …» o acción «Editar») y `produccion.cerrar` lo quita.
- `produccion.campo {clave: valor}` (comando del `form`): traduce los `select` (nombre de cliente → id por `nombre_norm`; código de contrato → id; «12 · Cuña Prueba» → 12) y, si hay `id`, llama a `editar` de la entidad; si es borrador, valida el formato de ese campo y lo guarda en el borrador. Los errores vuelven como 400 y la UI marca el campo en rojo con el mensaje (ya lo hace el renderer).
- `produccion.guardar`: `crear` con el borrador; si falla, guarda el mensaje en `produccion.aviso` y relanza el `ValueError`; si sale bien, la selección pasa al id nuevo.
- `produccion.archivados {entidad}` alterna ver activos/archivados; `produccion.pagina {entidad, offset}` pagina de a 50 («Anteriores»/«Siguientes», «51–100 de 230»).
- Pestañas: **Clientes** (Nombre · Contratos vigentes · acciones), **Contratos** (Código · Cliente · Tipo · Vigencia · Valor · Estado · acciones), **Pauta** (Contrato · Cliente · Cuña · Campaña · Cantidad · Vigencia · Franja · acciones). Encima de la tabla de la pestaña que coincide con la selección (posición y textos finales en «Propuesta de pantalla (A6a)»): título («Nuevo contrato» / «Contrato RRC-2026-001»), `form` y, si es borrador, «Guardar» y «Cancelar». Los nombres de cliente, códigos de contrato y títulos de cuña se leen por id con `ctx.entities.list(...)` (todas las páginas de cliente/contrato: decenas o cientos de filas).
- Selects: siempre con una opción vacía primera (si no, el navegador muestra la primera opción como elegida y no se puede «cambiar» a ella). Cuñas: `ctx.entities.list("pieza", where={"kind": "spot"}, limit=200)`, como «id · título»; si no hay ninguna, el formulario muestra «No hay cuñas en la biblioteca (carpeta «Spots»)».
- El panel tiene campos de texto: la UI ya no lo redibuja mientras un campo tiene el foco (`areas.js`), que es lo que pide la regla de `CLAUDE.md`. No hay `<iframe>` ni perillas.

### Cumplimiento (A6b, `estaciones/produccion/cumplimiento.py` + panel)
```python

    """[{compromiso_id, contrato, cliente, cuna, franja, contratado, emitido, faltan, estado, compartida}]"""
```
1. Compromisos no archivados (todas las páginas del `Registry`); `lo = min(window_start)`, `hi = max(window_end)`.
2. **Una** consulta de solo lectura (parámetros `?`, bajo `host.db_lock`): `SELECT started_at, asset_id, commitment_id FROM playlog WHERE status = 'completed' AND started_at >= ? AND started_at < ? AND (commitment_id IN (…ids) OR (commitment_id IS NULL AND asset_id IN (…cuñas)))`. Usa `idx_playlog_started`. Es una lectura directa del historial porque el `Registry` no tiene consultas por rango; no escribe (la prueba de «nadie escribe fuera del marco» sigue valiendo).
3. En Python: una emisión con `commitment_id` cuenta solo para ese compromiso (A7); sin `commitment_id`, para los compromisos de esa cuña cuya vigencia `[window_start, window_end)` la contiene y, si hay franja, cuya hora local (zona de la emisora) cae en `[desde, hasta)` (o fuera de `[hasta, desde)` si cruza la medianoche). Las fechas se comparan como `datetime` con zona (las de v1 terminan en `Z`, las nuevas en `+00:00`; `fromisoformat` lee ambas).
4. Estados del criterio 16; «atrasado» usa el ritmo lineal (`piso(contratado × transcurrido / duración)`).
5. **Caché** en memoria por `host`: clave = `(MAX(id) de playlog, MAX(updated_at) y COUNT(*) de commitments, MAX(updated_at) de contrato y cliente, ahora truncado al minuto, solo_vigentes)`; cinco agregados indexados por llamada en vez del cálculo. El panel se redibuja ~1 vez por segundo con la emisión en marcha: sin caché serían ~1 cálculo/s.

## Propuesta de pantalla (A6a)
Alcance: solo el panel «Comercial» (`produccion.comercial`). El panel de cumplimiento (A6b) se diseña aparte. Quien lo usa: una persona de Producción que no programa, en el PC de la emisora y a veces en el teléfono (modo red). Elementos usados, todos existentes en `uischema.py`: `label` (tonos `title`, `muted`, `ok`, `warn`), `button` (`md`, `sm`, `selected`), `table` con `UI.actions`, `form` (kinds `text`, `number`, `select`), `tabs`, `row`, `column`. Sin emojis, sin signos de exclamación, sin el nombre del dueño de la marca; colores y tipografías salen de los tokens (no se añade CSS). Tratamiento de «tú», como el resto de la plataforma.

### Flujo
1. **Entrar**: se abre el panel en la pestaña «Clientes» (la pestaña activa se recuerda). Se ve la lista de activos; una sola acción principal por pestaña: el botón grande «Nuevo cliente» / «Nuevo contrato» / «Nueva pauta». Orden natural de trabajo: Clientes → Contratos → Pauta (cada pestaña necesita la anterior; el estado vacío lo dice).
2. **Elegir qué hacer**: «Nuevo …» (arriba de la tabla) o «Editar» en la fila. Ambos ejecutan `produccion.ver`. El bloque de edición aparece **encima de la tabla**, entre los botones y la lista (el plan decía «debajo»; con 50 filas, en el teléfono el formulario quedaría fuera de vista tras pulsar «Editar»). Solo hay una selección a la vez.
3. **Editar una fila existente**: cada campo se guarda al salir de él (Tab, Enter o tocar otro lugar); queda un borde verde un instante. No hay botón «Guardar»; hay «Cerrar». Un campo inválido no se guarda: vuelve al valor anterior y aparece el aviso con el motivo.
4. **Crear**: el formulario nace vacío con «Guardar» y «Cancelar». Los campos se van anotando en el borrador; «Guardar» crea el registro, muestra «… creado.» y deja el formulario en modo edición sobre el registro nuevo (con «Cerrar»). «Cancelar» descarta el borrador sin preguntar (no se ha guardado nada).
5. **Archivar**: «Archivar» en la fila abre una confirmación en el mismo bloque superior (no un diálogo). Si hay dependientes no se ofrece el botón de confirmar: se explica qué archivar antes. Confirmar → el registro sale de la lista y aparece «… archivado.».
6. **Restaurar**: botón «Archivados» (grupo Activos / Archivados) → fila con «Restaurar», sin confirmación (es reversible y no cambia datos). Una pauta cuyo contrato sigue archivado no ofrece «Restaurar»: la fila dice qué hacer.

Reglas de formularios:
- Los selects siempre abren con una primera opción-guía («(elige …)») que `produccion.campo` interpreta como vacía. Reemplaza la «opción vacía» del plan: así se lee qué hay que hacer y se puede «volver» a ella.
- Fechas: el usuario escribe «DD/MM/AAAA»; `produccion.campo` también acepta «AAAA-MM-DD» y siempre guarda y muestra el formato de cada capa (la API sigue en AAAA-MM-DD). Valor: acepta «1.500.000», «$ 1.500.000» o «1500000».
- Debajo de «Franja hasta», línea muted: «Si la franja cruza la medianoche (de 22:00 a 02:00) también vale. Si la dejas vacía, cuenta todo el día.»
- Si hay 200 cuñas en el select, línea muted: «Se muestran las primeras 200 cuñas.» Si el valor mostrado por una pieza guardada ya no está en las opciones (archivada), se agrega al final como «12 · Cuña Prueba (archivada)» para no mostrar un select vacío.
- En el borrador, si un campo falla, el texto escrito se conserva en el borrador (no se pierde el trabajo) y el error sale en el aviso; se vuelve a validar en «Guardar». En edición de fila existente, el campo vuelve al valor guardado.
- Pie del formulario en edición: «Los cambios se guardan al salir de cada campo.» (mismo texto que el panel de streaming). En borrador: «Rellena los campos y pulsa «Guardar».»

### Textos exactos
Avisos de éxito (tono `ok`, en `produccion.listo`; se borran con el siguiente `ver`, `cerrar` o `campo` válido):
- «Cliente «Cliente Uno S.A.S.» creado.» · «Contrato RRC-2026-001 creado.» · «Pauta creada.»
- «Cliente «Cliente Uno S.A.S.» archivado. Puedes restaurarlo desde «Archivados».» · «Contrato RRC-2026-001 archivado. Puedes restaurarlo desde «Archivados».» · «Pauta archivada. Puedes restaurarla desde «Archivados».»
- «Cliente «Cliente Uno S.A.S.» restaurado.» · «Contrato RRC-2026-001 restaurado.» · «Pauta restaurada.»

Avisos de error (tono `warn`, en `produccion.aviso`): siempre «No se guardó: » + el mensaje del comando, que va en minúscula, sin punto interno y con la **etiqueta del formulario** (no el nombre de la columna). Al archivar o restaurar: «No se pudo archivar: …» / «No se pudo restaurar: …». Mensajes de los comandos (los marcados con * ya están fijados por los criterios 6, 7 y 10):

| Situación | Mensaje |
|---|---|
| Falta un dato obligatorio | «falta «nombre»»* · «falta «código»» · «falta «cliente»» · «falta «tipo»» · «falta «desde»» · «falta «hasta»» · «falta «contrato»» · «falta «cuña»» · «falta «cantidad»» |
| Nombre de cliente repetido | «ya existe un registro igual»* (el panel lo muestra como «No se guardó: ya existe un registro igual.»; recomendado ajustar el criterio 6 a «ya existe un cliente con ese nombre») |
| Código de contrato repetido | «ya existe un contrato con ese código» |
| Cliente archivado o inexistente | «elige un cliente activo» |
| Fecha mal escrita | ««desde» debe ser una fecha, por ejemplo 01/12/2026» (igual con «hasta») |
| `hasta` anterior a `desde` | ««hasta» no puede ser anterior a «desde»» |
| Valor con decimales | «el valor va en pesos, sin centavos»* |
| Valor con letras o negativo | «el valor debe ser un monto en pesos, por ejemplo 1.500.000» |
| Cantidad inválida | «la cantidad debe ser un número entero, de 1 en adelante» |
| Pauta fuera del contrato | «la pauta debe quedar dentro de la vigencia del contrato (01/12/2026 – 31/12/2026)» |
| Contrato archivado al crear/editar pauta | «el contrato está archivado: restáuralo primero» |
| Franja incompleta | «la franja necesita «desde» y «hasta», o déjala vacía» |
| Hora mal escrita | «la hora debe ir como HH:MM, por ejemplo 06:00» |
| Franja de un solo instante | «la franja no puede empezar y terminar a la misma hora» |
| Cuña no válida | «elige una cuña activa de la biblioteca» |
| Archivar cliente con contratos | «tiene contratos activos: archívalos primero»* |
| Archivar contrato con pautas | «tiene pautas activas: archívalas primero» (equivalente fijado por el criterio 10) |
| Restaurar pauta con contrato archivado | «su contrato está archivado: restáuralo primero» |
| Cualquier otra cosa inesperada | «ocurrió un problema al guardar. Vuelve a intentarlo; si sigue igual, avisa a quien administra la plataforma» (nunca SQL, rutas ni nombres de columnas) |

`preparar` valida lo obligatorio **antes** de pasar al `Writer` para que el mensaje use la etiqueta del formulario («código») y no la columna (`codigo`).

Confirmación de archivar (bloque superior, tono `title` + texto + dos botones; el primero es la acción principal):
- Sin dependientes: título «¿Archivar a «Cliente Uno S.A.S.»?» / «¿Archivar el contrato RRC-2026-001?» / «¿Archivar esta pauta?». Texto normal: «Dejará de aparecer en las listas y en los formularios. No se borra nada: puedes restaurarlo desde «Archivados».» (en pauta: «restaurarla»). Botones: «Archivar» y «Cancelar».
- Con dependientes (el panel lo comprueba al dibujar; no se ofrece «Archivar»): título «No se puede archivar todavía». Texto warn: ««Cliente Uno S.A.S.» tiene 2 contratos activos. Archívalos primero.» / «El contrato RRC-2026-001 tiene 3 pautas activas. Archívalas primero.». Botón único: «Entendido» (`produccion.cerrar`).
- Implementación: «Archivar» de la fila ejecuta `produccion.ver {entidad, id, archivar: true}` (sin comando nuevo); el botón «Archivar» de la confirmación llama a `<entidad>.archivar {id}`, que además deja el aviso de éxito y cierra la selección (los botones no muestran errores, por eso se comprueba antes).

### Accesibilidad y teléfono
- Todo es nativo (botones, tabla, `select`, `input`): foco con Tab, pestañas, Enter para guardar un campo. No hay atajos propios ni se agregan: el renderer no los admite y no hace falta.
- Estado y errores nunca van solo por color: el aviso trae texto; el campo en error lleva borde y mensaje en el aviso (el `title` del campo no se ve en el teléfono).
- En el teléfono: formulario de una columna (ya lo hace el CSS bajo 520 px), `narrow_hide` esconde columnas secundarias, «Editar» abre el formulario arriba de la tabla.
- Los campos de texto impiden el redibujado mientras tienen el foco (regla de `CLAUDE.md`); un aviso nuevo aparece al salir del campo.

## Riesgos
- Seguridad:
  - Escrituras solo por `host.entities.writer("produccion")`, todas con `risk="datos"` (prueba). En modo red los comandos exigen la clave (S6). Sin roles hasta A9: cualquiera con acceso puede crear o archivar contratos y ver valores; es el estado conocido del proyecto, se dice en el PR.
  - **Valores de contratos** visibles a todo usuario de la plataforma (y por `GET /api/entities/contrato`). Alternativa si el dueño lo prefiere: no guardar `valor_cop` hasta A9/B1 (se quita el campo de la declaración y del formulario; la columna puede crearse igual o no). Recomendación: guardarlo, opcional, porque sin valor el contrato pierde la mitad de su uso.
  - Datos personales: Cliente sin contacto ni documento; `notas`/`descripcion`/`notes` son texto libre, con aviso en el `placeholder` y en `docs/entidades.md`. Nada real en el repositorio.
  - SQL: ningún nombre de columna sale de la petición (las claves de la API pasan por `preparar`, que solo conoce las suyas); la consulta del historial usa `?` también para las listas `IN`. Mensajes de error escritos a mano.
  - El estado compartido (`produccion.sel`, borradores) es uno por servidor, no por usuario (igual que el explorador): dos personas editando a la vez verían la misma selección. Aceptable con un PC y un operador; con S7/A9 pasa a ser por sesión (deuda).
- Rendimiento y costo:
  - Panel «Comercial»: por redibujo ~5 consultas paginadas de decenas o cientos de filas (< 5 ms). Paginación de a 50; índices de orden en la migración.
  - Cumplimiento: sin caché, ~25 000 filas leídas y fechadas en Python ≈ 50–150 ms por cálculo; con caché, 5 agregados indexados por redibujo (< 2 ms) y un recálculo por emisión nueva (cada ~3 min) o por minuto. Criterio 17 lo mide.
  - Límite de variables de SQLite: 32 766 desde 3.32 (el equipo tiene 3.53.4); 600 compromisos + 600 cuñas caben de sobra.
- UX:
  - Las cuñas tocadas desde una carpeta que no está en la biblioteca se registran sin `asset_id` y **no cuentan**; tampoco las menciones en vivo. El panel lo dice en su línea gris: «Cuenta las emisiones completas de la cuña dentro de la vigencia y la franja (hora de la emisora). No cuenta cuñas tocadas fuera de la biblioteca ni menciones en vivo.»
  - Si las cuñas de RRC no están en una carpeta «Spots», no aparecen en el select (el escáner solo mapea `spots` → `spot`): verificación 2; el arreglo es de Programación (`library._FOLDER_KIND`), no de esta tarea.
  - «Cuña compartida»: dos compromisos vigentes con la misma pieza pueden contar dos veces la misma emisión hasta que A7 asigne cada emisión a un compromiso (`commitment_id`). Se marca en el panel en vez de prohibirlo (un cliente puede comprar dos campañas con la misma cuña en franjas distintas).
  - Los botones de la UI no muestran errores (solo `console.error`): por eso `produccion.aviso`. Los campos del formulario sí los muestran.
  - Pautas «por día» (5 diarias) se cargan como total (5 × días); el aviso de «atrasado» ayuda a ver el ritmo. Distribución diaria real: A7.
- Convivencia con el núcleo y con S10: choque de número de migración (regla anti-choque); `db.py` y `estaciones/__init__.py` los revisa el dueño. Si el dueño prefiere `Field(default=...)` en `entities.py` en lugar del marcador `"(ver contrato)"`, es un cambio de ~5 líneas en el núcleo, con prueba, y Producción deja de pasar `client`; el resto del plan no cambia. Recomendación: el marcador (no toca el marco).
- Concurrencia: la edición es campo por campo, así que dos ediciones simultáneas de la misma fila solo chocan si tocan el mismo campo (gana la última). Sin campo `version` en esta tarea (deuda heredada de S8, sigue abierta).
- `playlog.commitment_status` (núcleo) sigue existiendo con su lógica de v1 (sin franja, sin cuña): no lo usa nadie fuera de `test_core.py`. No se toca; unificar o retirarlo lo decide el dueño (deuda).
