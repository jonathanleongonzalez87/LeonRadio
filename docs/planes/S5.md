# S5 — Núcleo: base de datos persistente y compartida

Sin BLOQUEO: no hace falta nada del usuario para implementarla. Datos de infraestructura: corre local en el PC de la emisora (Windows), sin hosting ni cron; la base vive en `%LOCALAPPDATA%` (no sincronizado por OneDrive, a propósito: SQLite + OneDrive corrompe archivos). `origin/main` verificado: último commit `fb96a58` (Monitores / modo red); S5 no está mergeada y no hay plan previo en `docs/planes/` (sin deuda heredada).

## Objetivo
Que el historial de emisión (`playlog`) y la biblioteca sobrevivan a reiniciar LeonRadio: la base es un archivo propio del usuario, con esquema versionado, copias de seguridad automáticas y un escaneo que solo procesa lo nuevo o cambiado.

## Criterios de aceptación

- [ ] Persistencia: crear `Host(db_path=tmp/x.db)`, registrar una emisión, cerrar, abrir otro `Host` con la misma ruta: el `playlog` y los `assets` siguen ahí.
- [ ] `leonradio serve --audio null --library "..\Rockland Radio"` dos veces seguidas: el 2.º arranque no reinserta piezas (mismo `COUNT(*)` de `assets`, mismos ids) y el escaneo tarda una fracción del 1.º (solo `stat`, sin hashear).
- [ ] Base creada con el esquema viejo (sin `user_version`, con y sin la columna `playlog.file_type`) se abre, queda en `user_version = len(MIGRATIONS)` y conserva todas sus filas.
- [ ] Base con `user_version` mayor que el código conoce: error claro («creada por una versión más nueva de LeonRadio») y no se modifica.
- [ ] Copia de seguridad: al arrancar con una base existente aparece `copias\leonradio-AAAAMMDD-HHMMSS.db` junto a la base, abrible con `sqlite3` y con las mismas filas; nunca más de 7 copias (la 8.ª borra la más vieja).
- [ ] Escaneo incremental: archivo borrado de la carpeta → su fila pasa a `status='retired'` sin borrarse (el `playlog` que lo referencia intacto); si el archivo vuelve, pasa a `active` con el mismo id; archivo modificado (tamaño/mtime distinto) se re-lee; carpeta de la biblioteca inexistente o vacía de golpe NO retira nada.
- [ ] La ruta de la base y de las copias solo sale de `--db`, `LEONRADIO_DB` o el valor por defecto: ningún endpoint ni comando acepta una ruta de base/copia (`grep` de `db_path` en `server.py`/`builtin/` lo confirma).
- [ ] Al cerrar el servidor (Ctrl+C) se hace checkpoint del WAL y se cierra la conexión; queda un único `leonradio.db` coherente (el `-wal` vacío o ausente).

## Diseño

### Ruta de la base (`settings.py`)
Nueva `db_path() -> Path`, precedencia: (1) `--db` (argumento explícito), (2) variable `LEONRADIO_DB`, (3) si existe `LEONRADIO_CONFIG` → `<carpeta de ese archivo>/leonradio.db` (las pruebas quedan aisladas con su config temporal), (4) `%LOCALAPPDATA%\LeonRadio\leonradio.db` (o `~/.config/leonradio/leonradio.db`). Reutiliza `path().parent`. Crea la carpeta al abrir (`mkdir(parents=True, exist_ok=True)`).

**Seguridad de las pruebas:** `create_app(db_path=":memory:")` conserva su valor por defecto. La ruta real solo se resuelve en `serve()` (y en `cli scan`). Así ninguna prueba que llame `create_app()` o `Host()` sin ruta puede tocar la base del usuario.

### Migraciones (`db.py`)
`SCHEMA` deja de ser un script monolítico: se reemplaza por una lista ordenada `MIGRATIONS: list[Callable[[sqlite3.Connection], None]]` (o cadenas SQL); el índice + 1 es la versión. La versión vive en `PRAGMA user_version`.

```python
def _m1_esquema_inicial(conn):
    conn.executescript(SCHEMA_V1)          # el SCHEMA actual, sin el PRAGMA; todo IF NOT EXISTS
    cols = {r["name"] for r in conn.execute("PRAGMA table_info(playlog)")}
    if "file_type" not in cols:            # bases previas a F1 (sustituye el ALTER suelto de connect)
        conn.execute("ALTER TABLE playlog ADD COLUMN file_type TEXT NOT NULL DEFAULT 'audio'")

def _m2_escaneo_incremental(conn):
    conn.execute("ALTER TABLE assets ADD COLUMN size_bytes INTEGER")
    conn.execute("ALTER TABLE assets ADD COLUMN mtime_ns INTEGER")

MIGRATIONS = [_m1_esquema_inicial, _m2_escaneo_incremental]   # nunca se edita una ya publicada: se agrega otra
```

`migrate(conn)`: lee `user_version`; si `> len(MIGRATIONS)` → `RuntimeError` con el mensaje de arriba; por cada migración pendiente: `BEGIN IMMEDIATE` → migración → `PRAGMA user_version = n` → `COMMIT` (`ROLLBACK` si falla y se re-lanza; `user_version` se revierte con la transacción). La migración 1 es idempotente, por eso una base antigua sin `user_version` (=0) pero con tablas pasa limpia. `executescript` hace COMMIT implícito, por lo que dentro de la transacción las migraciones usan `conn.execute` por sentencia (el desarrollador divide `SCHEMA_V1` en sentencias, o lo corre fuera del `BEGIN` aprovechando que todo es `IF NOT EXISTS`; elegir lo primero que pase la prueba de reversión). `PRAGMA foreign_keys = ON` se ejecuta por conexión en `connect()` (no es persistente y no puede ir dentro de transacción).

Regla para el futuro (documentarla en `docs/entidades.md`, que ya dice «con migración»): cambiar el esquema = agregar una función al final de `MIGRATIONS` + una prueba; nunca editar las anteriores. Las tablas de S8 (Programa, Persona…) serán la migración 3 y siguientes.

### Concurrencia (decisión)
Se mantiene **una sola conexión compartida** (`check_same_thread=False`, que ya es `shared=True`) protegida por `host.db_lock` (RLock existente), y se agrega:
- `PRAGMA journal_mode=WAL`: el lector (UI, `leonradio scan` desde otra consola, una herramienta externa) no bloquea al escritor (hilo de audio que registra emisiones) y un corte de luz no corrompe la base.
- `PRAGMA synchronous=NORMAL` (seguro con WAL; solo puede perder la última transacción ante corte del sistema, aceptable para un as-run log que escribe una fila por pieza) y `PRAGMA busy_timeout=5000` (si otro proceso escribe a la vez, espera en vez de fallar).
- Por qué NO una conexión por hilo: los hilos ya serializan con `db_lock`; `:memory:` (pruebas) requiere una única conexión; cambiarlo tocaría `playout.py`, `sdk.py`, `demo_web.py` y las 50 pruebas sin ganar nada con ~1 escritura por pieza. Por qué no solo el lock sin WAL: sin WAL, el modo `DELETE` bloquea lectores externos y es más frágil ante cortes.
- WAL en `:memory:` devuelve `memory`: se ignora sin error. La base debe estar en disco local (lo está: `%LOCALAPPDATA%`); documentarlo.
- `connect()` queda: `connect(path=":memory:", *, shared=False)` → abre, aplica PRAGMAs, `migrate()`. Se agrega `close(conn)` (checkpoint `wal_checkpoint(TRUNCATE)` + `close()`), llamada desde el `lifespan` del servidor tras `playout.stop()`.
- Regla de uso: todo acceso desde hilos usa `with host.db_lock`. `library.scan` recibe `lock` (igual que `add_file`) y lo toma solo por lote.

### Copia de seguridad (`backup.py`, nuevo)
`make_backup(db_path, keep=7, min_interval_s=3600) -> Path | None`, llamada desde `Host`/`serve` ANTES de `migrate()` (así también queda copia previa a una migración):
1. Si la base no existe o está vacía (primer arranque) o `:memory:` → no hace nada.
2. Carpeta `<carpeta de la base>/copias/`. Si la copia más reciente tiene < 1 h (`min_interval_s`), no copia, salvo `force=True` cuando hay migraciones pendientes (`user_version < len(MIGRATIONS)` y > 0). Esto evita que 7 reinicios seguidos de depuración borren todas las copias útiles; el valor se puede bajar a 0 en pruebas.
3. Copia consistente con `src.backup(dst)` (API de backup de SQLite, válida con WAL y con la base en uso) hacia `leonradio-AAAAMMDD-HHMMSS.db.tmp` y luego `os.replace` al nombre final (atómico); si falla se borra el `.tmp`.
4. Rotación: ordena por nombre (el sello hace que orden alfabético = cronológico), borra las sobrantes salvo las `keep` más recientes. Solo borra archivos que cumplan el patrón `leonradio-*.db`.
5. Un fallo de copia (disco lleno, permisos) se registra con `log.warning` y NO impide arrancar.
Restaurar: documentado en `docs/` (cerrar LeonRadio, copiar la copia elegida sobre `leonradio.db` y borrar `leonradio.db-wal`/`-shm`). Sin comando de restauración en esta tarea.

### Escaneo incremental (`library.py`)
`scan(conn, root, *, lock=None, progress=None, cancel=None) -> dict` con `{added, duplicates, updated, retired, reactivated, unchanged, cancelled}`.
1. Recorre `root` (como hoy) acumulando `seen: set[str]`.
2. Por archivo, `st = p.stat()`:
   - No está en `assets` → se inserta (hash, tags, duplicado por hash; guarda `size_bytes`, `mtime_ns`). Igual que hoy.
   - Está con `size_bytes`/`mtime_ns` iguales → `unchanged`, sin leer el archivo. Si estaba `retired` → vuelve a `active` (`reactivated`), conservando id.
   - Está pero `size_bytes`/`mtime_ns` son NULL (fila previa a la migración 2) → solo rellena esos dos campos (sin re-hash; coste cero).
   - Está pero cambió → re-lee hash y tags, `UPDATE` de esa fila (mismo id), `updated`.
3. Al terminar SIN cancelar: las filas con `path` bajo `root` (comparación por prefijo de carpeta, no por `LIKE %`), `status IN ('active','duplicate')` y no vistas pasan a `retired` — ninguna se borra. Las piezas agregadas con `add_file` desde fuera de `root` no se tocan.
4. Salvaguardas contra el desastre «se desconectó el disco / OneDrive sin conexión»: si `root` no es un directorio, o si no se vio ningún audio pero había filas activas bajo `root`, no se retira nada (se devuelve `retired=0` y un `warning` en el log).
5. `progress(done, total_estimado)` y `cancel()` (callable que devuelve bool): se consultan por archivo; commit por lote de 200 archivos (con `lock` si se pasó), de modo que cancelar o un corte conservan lo ya hecho y relanzar continúa. En `serve()` el escaneo sigue siendo síncrono al arrancar (como hoy) pero imprime progreso cada 500 archivos y Ctrl+C lo cancela limpiamente; mover el escaneo a un hilo con barra en la UI queda como deuda (necesita diseño de UI).
6. `retired` ya queda excluido de todas las consultas actuales (`WHERE status='active'` en `sdk.py`, `playout.py`, `library.py`), así que una pieza desaparecida deja de ofrecerse sin romper el historial (`playlog.asset_id` no cambia; el título ya está copiado).

### Cableado (`server.py`, `sdk.py`, `cli.py`)
- `serve(..., db: str | None)`: `db_path = args.db or settings.db_path()`; imprime «Base de datos: <ruta>» al arrancar. Llama `backup.make_backup` y luego `create_app(db_path=...)`.
- `create_app` conserva `db_path=":memory:"` por defecto; al apagar llama `db.close(host.db)` dentro del `lifespan` (bajo `db_lock`).
- `sdk.Host.__init__` no cambia de firma.
- `cli.py`: `serve --db RUTA` (por defecto `os.environ.get("LEONRADIO_DB")` → `settings.db_path()`); `scan --db` pasa a usar el mismo valor por defecto (hoy es `leonradio.db` en la carpeta actual, lo que dejaría una base distinta de la del servidor) e imprime el nuevo resumen del escaneo.
- `iniciar-leonradio*.bat` no cambian (heredan el valor por defecto).

## Riesgos
- Seguridad: la ruta de la base y de las copias no llega por red ni por el navegador: solo CLI/variable de entorno/valor por defecto; la rotación solo borra `leonradio-*.db` dentro de `copias/`. Las copias contienen el historial y rutas locales: quedan en `%LOCALAPPDATA%` del usuario (permisos por defecto de su perfil) y fuera del repo (`.gitignore`). Ninguna clave vive en la base (la clave de Icecast sigue en `config.json`). La validación de rutas que llegan del navegador (Explorador, cargar archivo) sigue siendo S6, no esta tarea; hay que corregir `CLAUDE.md` para que no diga que S5 la cierra.
- Rendimiento y costo: biblioteca real estimada en ~10.000 archivos. 1.er escaneo: dominado por hash + mutagen (hoy ya ocurre en cada arranque; ~minutos según disco). Arranques siguientes: 10.000 `stat` + 10.000 consultas por índice (`path` UNIQUE) ≈ 1–3 s. Base ~5–10 MB; 7 copias ≈ 35–70 MB, trivial en disco local. Copia con la API de backup: <1 s a ese tamaño. WAL: una fila por pieza emitida, coste despreciable. El escaneo tiene un `Path.rglob` completo en cada arranque aunque no haya cambios (aceptable; vigilancia por eventos queda fuera).
- UX: el arranque con un `leonradio.db` ya existente muestra «Base de datos: <ruta>» y el resumen del escaneo (nuevas/retiradas) en consola; un error de versión futura o de base corrupta se imprime en español y detiene el arranque en vez de crear una base vacía sin avisar. El usuario con una base de prueba anterior en la carpeta del proyecto (`leonradio.db` del CLI viejo) no se migra sola: es otra base; se puede abrir con `--db`.
- Peligro de dos procesos: dos servidores sobre la misma base no están soportados (el sondeo de puerto ya evita el caso normal); el `busy_timeout` solo cubre escrituras ocasionales de `scan`/herramientas externas.
- `synchronous=NORMAL` puede perder la última transacción ante un corte del sistema (no ante cierre de la app); se acepta y se anota.
- La salvaguarda de «nada visto» podría impedir retirar legítimamente una carpeta vaciada a propósito; se acepta (avisa por log) frente al riesgo contrario.
