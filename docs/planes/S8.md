## Diseño

### Tres piezas, una en cada capa
1. **Marco** (`core/src/leonradio_core/entities.py`, nuevo): declaraciones, registro y servicio. Núcleo; lo revisan los dueños de las estaciones.
2. **Declaración + migración de cada estación**, dentro de su carpeta: `estaciones/<estacion>/entidades.py` (qué entidades tiene) y `estaciones/<estacion>/migraciones.py` (SQL literal, sin importar nada del paquete).
3. **Lectura para todos**: REST `GET /api/entities*`, `Context.entities` y el panel «Entidades».

### Declaración
```python
@dataclass(frozen=True)
class Field:
    name: str                      # identificador: ^[a-z][a-z0-9_]{0,40}$
    type: str = "text"             # text | int | real | bool | date (AAAA-MM-DD) | datetime (ISO 8601 UTC)
    required: bool = False
    ref: str | None = None         # nombre de otra entidad: el valor es su id
    choices: tuple[str, ...] | None = None
    unique: bool = False           # solo documenta; el índice UNIQUE vive en la migración (la prueba de deriva lo comprueba)
    derived_from: str | None = None  # campo calculado por el servicio (p. ej. nombre_norm de nombre); quien llama no lo envía
    max_len: int = 200             # texto; 2000 para notas largas

@dataclass(frozen=True)
class Entity:
    name: str                      # singular, español, sin tildes: "artista"
    table: str                     # normalmente igual; "assets" en Pieza
    owner: str                     # clave de STATIONS: "programacion"
    label: str                     # «Artista»
    about: str                     # una línea para el panel
    fields: tuple[Field, ...]      # SOLO lo que se expone y se puede escribir (las columnas estándar no se declaran)
    title: str = "nombre"          # campo que identifica la fila al mostrarla
    managed: bool = True           # False = tabla anterior al marco: solo lectura por el servicio (Pieza, Registro de emisión, Compromiso)
    active_sql: str | None = None  # solo managed=False: condición fija escrita en código (p. ej. "status = 'active'") para contar «activos»
    note: str = ""                 # nota para el panel («a rediseñar en A6»)
```
Entidad gestionada = tabla con las columnas estándar `id INTEGER PRIMARY KEY, archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1)), created_at TEXT NOT NULL, updated_at TEXT NOT NULL, created_by TEXT NOT NULL, updated_by TEXT NOT NULL` más las columnas de `fields`. Las referencias se declaran en SQL con `REFERENCES otra(id)` **sin** `ON DELETE CASCADE` (el borrado no existe; si alguien borrara a mano, el motor lo impide mientras haya referencias).

Regla de oro técnica: **ningún identificador de columna o tabla viene de una petición**. Todos salen de las declaraciones, validadas con la expresión regular al declararlas; los valores van siempre como parámetros `?`.

### Servicio (`Registry`, en `host.entities`)
`Host.__init__` crea `self.entities = entities.Registry(self)` (usa `host.db` y `host.db_lock`). Interfaz:

```python
class Registry:
    def declare(self, entity: Entity) -> None
    def validate(self) -> None                       # refs, dueños; lo llama register_all al final
    def get_entity(self, name) -> Entity;  def all(self) -> list[Entity]
    # lectura (cualquiera)
    def list(self, name, *, limit=50, offset=0, include_archived=False, where: dict | None = None) -> dict
    def get(self, name, id: int) -> dict
    def catalog(self) -> list[dict]                  # para el panel y GET /api/entities (cuenta activos/archivados)
    # escritura (solo por el writer de la estación dueña)
    def writer(self, station: str) -> "Writer"       # station debe estar en STATIONS
    def transaction(self)                            # context manager: varias escrituras, un commit (rollback si falla)

class Writer:                                         # create/update/archive/restore; cada una exige entity.owner == self.station
    def create(self, name, values: dict, who: str) -> int
    def update(self, name, id: int, values: dict, who: str) -> None
    def archive(self, name, id: int, who: str) -> None
    def restore(self, name, id: int, who: str) -> None
```
Comportamiento:
- **Dueño comprobado en el servicio**: el `Writer` conoce su estación; cada método busca la entidad y lanza `sdk.PermissionDenied(f"«{label}» la escribe {dueño}")` si no coincide. `managed=False` → `ValueError("esa información la mantiene el sistema")`. Es una capacidad: una estación solo obtiene el writer de **su** clave porque su `register(host)` lo pide con su nombre; la comprobación evita errores de una estación, no un módulo malicioso (los addons no tienen acceso a `writer`; ver Riesgos).
- **Validación**: tipos (int/real/bool/date), `required` en `create`, `choices`, `max_len`, `ref` (la fila existe y `archived=0`; se comprueba solo si el valor cambió), campos desconocidos o `derived_from` → `ValueError`. `derived_from` se calcula con `norm(texto) = unicodedata.normalize("NFC", s).strip().casefold()` colapsando espacios.
- **Unicidad**: el `UNIQUE` vive en la base; un `sqlite3.IntegrityError` se traduce a `ValueError("ya existe un registro igual")` o `ValueError("la referencia no existe")` sin texto SQL.
- **Marcas**: `created_at/updated_at` = `datetime.now(timezone.utc).isoformat(timespec="milliseconds")`; `created_by/updated_by` = `who`.
- **Una escritura = una transacción** bajo `with host.db_lock` y `commit` (o dentro de `transaction()`, que cuenta profundidad y hace commit solo al salir del nivel exterior). Al final emite `host.events.emit("entities.changed", {"entity": nombre, "id": id, "action": "create|update|archive|restore"})` (los paneles abiertos se redibujan solos).
- **Lectura**: `SELECT <id + campos declarados + archived + created_at + updated_at + created_by + updated_by> FROM tabla WHERE …` (para `managed=False`, solo `id` + campos declarados). `ORDER BY` el campo `title` y luego `id` (determinista para paginar). `where={"artista_id": 3}` → `AND artista_id = ?` solo si el campo está declarado. Con `include_archived=False` agrega `archived = 0` (o `active_sql`).
- **Comprobación de deriva** `check_declaration(conn, entity) -> list[str]`: compara columnas y `REFERENCES` de `PRAGMA table_info/foreign_key_list` con la declaración y devuelve diferencias. `register_all` la corre por cada entidad y solo **avisa por log** (no tumba el arranque); la prueba de cada estación la exige vacía.

### Principal y nivel de riesgo (punto de conexión con S7)
- `sdk.Context.__init__(host, owner, permissions, principal: str = "local")` y `Host.run_command(name, args=None, principal="local")`; `server.run` recibe `who: auth.Principal = Depends(auth.current_principal)` (hoy lo declara en `dependencies=`) y pasa `who.id`. Los comandos leen `ctx.principal`. Defecto `"local"` mantiene las pruebas actuales. **S7 solo cambia el cuerpo de `current_principal`**; el `Principal` que llega a las filas pasa a ser el usuario sin tocar las estaciones.
- `sdk.RISKS` suma `"datos"` (escritura de entidades compartidas). `register_crud` registra con `risk="datos"`; los comandos propios de una estación que escriban entidades deben hacerlo igual (lo dice el contrato).
- `PERMISSIONS` suma `"entities.read"`; `Context.entities` (solo `list/get/catalog`) lo exige. Los addons que ya declaran permisos no se ven afectados (no se les pide el nuevo).

### Comandos y REST
- `entities.register_crud(host, station, names)` registra, por cada entidad, `<nombre>.crear(**campos)`, `.editar(id, **campos)`, `.archivar(id)`, `.restaurar(id)` (owner `"builtin"` como el resto de estaciones, riesgo `datos`). Cada uno llama al `Writer` de `station` con `ctx.principal`. Es opcional: una estación con una pantalla propia puede registrar sus comandos a mano usando el `Writer`.
- Lectura REST en `server.py` (los tres `GET`, ver criterio 8). Lectura desde Python: `ctx.entities.list(...)`. No hay comandos POST de lectura (evita duplicar).
- Tamaños: el límite del cuerpo de S6 (256 KiB) ya cubre las escrituras; `max_len` por campo cubre el resto.

### Migraciones (qué y dónde)
Cada migración es una función `m<N>_<tema>(conn)` con SQL literal (nunca generado desde la declaración: una migración publicada no puede cambiar). Viven en `estaciones/<estacion>/migraciones.py` y **solo importan `sqlite3`/`unicodedata`**. `db.py` las agrega al final de `MIGRATIONS`:

```python
MIGRATIONS = [_m1_esquema_inicial, _m2_escaneo_incremental,
              programacion_migraciones.m3_catalogo_musical,      # S8a
              direccion_migraciones.m4_programa_y_persona,       # S8b
              al_aire_migraciones.m5_invitado]                   # S8b
```
Ciclo de importación: `db.py` importa esas funciones **al final del módulo**; `estaciones/__init__` hace `from .. import sdk`, y `sdk` importa `db` pero solo lo usa en tiempo de ejecución, por lo que funciona en ambos órdenes de import. Si la prueba del criterio 11 falla, plan B (sin discusión): mover las funciones a `core/src/leonradio_core/esquema/<estacion>.py` (sin dependencias) y que `db.py` importe desde ahí; el resto del plan no cambia.

Regla anti-choque (dos PR que agregan migración a la vez): una prueba exige que `MIGRATIONS[i].__name__` cumpla `^_?m{i+1}_`; si dos ramas agregan «m4», la segunda en mergear **renumera su función** al rebasar (solo es posible mientras la migración no se haya publicado; la lista es de código, no de datos). Quien ya aplicó la suya en su base local la restaura de `copias\` o usa otra base. Si el PR de A6 llega antes que S8b, A6 toma m4 y S8b pasa a m5/m6 sin otro cambio.

### S8a — migración 3 (`programacion/migraciones.py::m3_catalogo_musical`)
Tablas (todas con las columnas estándar):
- `genero(nombre, nombre_norm UNIQUE)`.
- `artista(nombre, nombre_norm UNIQUE, notas)`.
- `album(titulo, titulo_norm, artista_id REFERENCES artista(id), anio INTEGER)`; índice único `(COALESCE(artista_id, 0), titulo_norm)` (un mismo título en dos artistas sí es posible; sin artista, uno por título).
- `ALTER TABLE assets ADD COLUMN artista_id INTEGER REFERENCES artista(id)`, `album_id … album(id)`, `genero_id … genero(id)` (todas NULL por defecto: `ALTER ADD COLUMN` con `REFERENCES` y `foreign_keys=ON` exige default NULL, que es el caso) e índices `idx_assets_artista`, `idx_assets_album`. Un artista principal por pieza; colaboraciones («feat.») quedan para A3/A2 (ver deuda).
- Relleno en la misma transacción, en Python (no en SQL: el `lower()` de SQLite solo conoce ASCII y no uniría «Beyoncé»/«BEYONCÉ»): lee `SELECT DISTINCT artist FROM assets WHERE artist IS NOT NULL AND trim(artist) <> ''`, agrupa por `norm()`, inserta un `artista` por grupo con el nombre más frecuente como `nombre` (`created_by='sistema'`), actualiza `assets.artista_id` por coincidencia de `norm`; lo mismo para `(artista_id, album)` → `album`. La migración copia su propia `norm` (no importa la del marco: congelada). Los textos `assets.artist`/`album` **no se tocan** (el historial y el escáner siguen igual; el historial no se vincula a nada nuevo).
- Idempotente: `CREATE TABLE IF NOT EXISTS`, `INSERT OR IGNORE`, `UPDATE … WHERE artista_id IS NULL`; el `ALTER` solo corre si la columna no existe (`PRAGMA table_info`). La reversión es la copia previa: `backup.make_backup(force=True)` ya corre antes de toda migración pendiente (S5); se comprueba en prueba.
- Costo: ~10 000 piezas, ~1 500 artistas: un `SELECT DISTINCT`, ~1 500 inserciones y un `UPDATE` indexado ≈ < 1 s, una sola vez.

### S8a — sincronización con el escaneo (`programacion/catalogo.py`)
- `sync(host) -> dict`: bajo `host.entities.transaction()` y `writer("programacion")` con `who="sistema"`: (1) piezas con `artista_id IS NULL` y artista de texto no vacío → buscar por `nombre_norm`, crear si falta, vincular; (2) lo mismo con álbum (`album_id IS NULL`, texto no vacío; usa el `artista_id` ya resuelto). Estado estable = una consulta de 10 000 filas sin resultados (< 50 ms, sin escribir).
- Se llama desde `programacion.register(host)`: en `create_app` el escaneo corre **antes** de `register_all`, así que el sync ve las piezas recién escaneadas sin tocar `server.py`. Comando `catalogo.sincronizar` (`risk="datos"`, dueño Programación) para el caso de piezas agregadas con `add_file` en caliente; no se agrega nada a la lógica de `add_file`.
- `library.scan`, cambio mínimo (la tabla `assets` es de Programación): en la rama «cambió» (`UPDATE`), si el artista o el álbum de texto cambian respecto a lo guardado, esa fila pone `artista_id`/`album_id` en `NULL` para que el próximo `sync` la re-vincule. El `SELECT` previo suma `artist, album` (misma consulta, dos columnas más). No cambia ids, `size_bytes/mtime_ns` ni el retiro.
- Género: `assets` no guarda género (`meta.py` solo lo lee de las etiquetas al vuelo); no hay relleno de `genero_id`. Dejar `genero`/`genero_id` listos para A3/A2 (deuda).

## Contrato para quien desarrolla otra estación (va tal cual a `docs/entidades.md`)
Para agregar una entidad nueva a tu estación (ejemplo ficticio: **Sala** de grabación, dueña Producción):

1. **Mira `docs/entidades.md`**: si existe, úsala (referénciala por id).
2. **Declárala** en `estaciones/produccion/entidades.py`:
```python
from ...entities import Entity, Field
SALA = Entity("sala", "sala", owner="produccion", label="Sala de grabación", about="Espacio donde se graba",
              fields=(Field("nombre", required=True), Field("nombre_norm", derived_from="nombre", unique=True),
                      Field("capacidad", "int"), Field("estado", choices=("libre", "ocupada"))))
# en estaciones/produccion/__init__.py:
def register(host):
    host.entities.declare(SALA)
    entities.register_crud(host, "produccion", ["sala"])      # sala.crear / .editar / .archivar / .restaurar
```
3. **Migración** en `estaciones/produccion/migraciones.py` (solo `sqlite3`, SQL literal, idempotente) y agregada al **final** de `MIGRATIONS` en `db.py` con el nombre `m<N>_…` (N = su posición):
```python
def m6_sala(conn):
    conn.execute("""CREATE TABLE IF NOT EXISTS sala (id INTEGER PRIMARY KEY,
        nombre TEXT NOT NULL, nombre_norm TEXT NOT NULL UNIQUE, capacidad INTEGER, estado TEXT,
        archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1)),
        created_at TEXT NOT NULL, updated_at TEXT NOT NULL, created_by TEXT NOT NULL, updated_by TEXT NOT NULL)""")
```
   Nunca se edita una migración ya publicada; para cambiar una tabla, otra migración (`ALTER TABLE … ADD COLUMN`).
4. **Referencias por id**: un campo `Field("cliente_id", "int", ref="cliente")` y `REFERENCES cliente(id)` en el SQL. Jamás copies el nombre del cliente a tu tabla. Leer la entidad de otra estación: `ctx.entities.list("cliente")`; escribirla: no se puede (pídelo a su dueña).
5. **Borrado**: no existe; `archivar` (y `restaurar`). Los comandos propios que escriban llevan `risk="datos"` y usan `host.entities.writer("produccion")` con `ctx.principal`.
6. **Prueba** (`core/tests/test_<tu_estacion>_entidades.py`, base `:memory:`, datos inventados):
```python
def test_sala(host):                               # fixture: Host(":memory:") con register_all
    assert entities.check_declaration(host.db, SALA) == []          # el SQL de la migración coincide con la declaración
    w = host.entities.writer("produccion")
    sid = w.create("sala", {"nombre": "Sala Uno", "capacidad": 4}, who="local")
    w.archive("sala", sid, who="local")
    assert host.entities.list("sala")["total"] == 0                 # archivada: sigue en la base
    with pytest.raises(sdk.PermissionDenied): host.entities.writer("direccion").create("sala", {"nombre": "X"}, who="local")
```
7. Agrega la fila a `docs/entidades.md` (`existe`) **en el mismo PR**; una prueba del núcleo falla si falta.

La misma prueba de ejemplo vive en `core/tests/test_entities.py` con una entidad ficticia propia, de modo que el contrato está comprobado por el propio marco.

## Riesgos
- Seguridad:
  - Inyección SQL: ningún nombre de tabla/columna viene de la petición; salen de declaraciones validadas por expresión regular, y los valores van por `?`. Prueba explícita del intento en `where`.
  - Dueño = comprobación de capacidad, no sandbox: un módulo de estación o un addon con acceso a `host` podría tomar `writer("otra")`. Los addons no reciben `host` ni `writer` (usan `Context`, que solo ve `entities.read`); las estaciones son código del repositorio y las revisa el dueño de cada una. Permisos reales por usuario y rol: S7.
  - Autenticación: los tres `GET` llevan `current_principal` como el resto; en modo local es sin clave (decisión de S6). Las respuestas solo traen columnas declaradas (no `path` de archivos del PC, no `notes` de compromisos, no `sha256`).
  - Datos personales: Persona e Invitado guardan solo nombre y notas; sin contacto ni documento. Pruebas y docs con nombres inventados; ningún dato real en el repositorio. Riesgo UX/privacidad: `notas` es texto libre y podría contener datos sensibles: se avisa en `docs/entidades.md`.
  - Errores: `IntegrityError` y mensajes SQL no llegan al navegador (traducidos a mensajes fijos); sin `str(exc)` genérico en el servicio.
  - Copias de seguridad: las nuevas tablas quedan en la copia de S5; la migración 3 es la primera que reescribe contenido de la base real, por eso la verificación 1 se hace sobre una copia.
- Rendimiento y costo: biblioteca ~10 000 piezas, ~1 500 artistas, ~1 000 álbumes. Migración 3: < 1 s, una vez. Arranque posterior: una consulta indexada de 10 000 filas ≈ < 50 ms. Listados: paginados, máx. 200 filas por llamada, `ORDER BY` con índice en el título (`nombre_norm`/`titulo_norm` para artista y álbum). El panel hace 1 `COUNT` por entidad (≈ 8 entidades) por redibujo: despreciable. El panel se redibuja con `entities.changed`: una escritura por lotes (`sync` con 1 500 creaciones) emite 1 evento al cerrar `transaction()`, no 1 500 (los eventos se acumulan y salen al `commit` exterior).
- UX: sin pantallas de edición en esta tarea (las hará cada estación); el panel solo informa. «Unificar» artistas por mayúsculas/tildes es automático y puede juntar dos artistas distintos con el mismo nombre (homónimos): para eso el `UNIQUE` es por `nombre_norm` y la deuda registra «separar/fusionar artistas» como función de Programación. Si Programación quiere un artista distinto con el mismo nombre, hoy no puede (la base lo impide): decisión anotada, a revisar con A2.
- Convivencia con A6 (otra persona, en paralelo): choque de números de migración (regla de renumeración + prueba de nombres) y de `db.py`/`sdk.py`, que son núcleo y los revisan ambos. El marco no inventa campos de Producción: `commitments` queda intacta.
- Riesgo de ciclo de importación `db` ↔ `estaciones` ↔ `sdk` (arriba): prueba con `subprocess` y plan B definido.
- `PRAGMA foreign_keys=ON` y `ALTER TABLE ADD COLUMN … REFERENCES`: solo permitido con default NULL (es el caso); si una versión de SQLite del equipo lo rechaza, la prueba de migración falla en CI y se agrega la columna sin `REFERENCES` más un índice (la comprobación de existencia pasa a la capa de servicio, que de todos modos la hace).
